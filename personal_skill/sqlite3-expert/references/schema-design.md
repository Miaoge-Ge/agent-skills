# 表结构设计和 DDL 审查

## 设计顺序

1. 定义每行的业务含义和生命周期：当前任务、某次执行、某次修订或历史快照不能混为一谈。
2. 列出候选键、字段间依赖、一对多/多对多关系以及最常见的查询与写入。
3. 通常从第三范式开始；把“实体属性”和“关系属性”放对表。是否反范式由查询成本、快照语义及一致性维护方式决定。
4. 决定主键、NULL/默认值、业务唯一性、范围限制、外键及删除策略。
5. 再选择 rowid/STRICT/WITHOUT ROWID 和索引；不要从索引反推不成立的业务规则。

## 主键和唯一性

- INTEGER PRIMARY KEY 在通常写法下是 rowid 的别名，可省略值自动分配；INT PRIMARY KEY、BIGINT PRIMARY KEY 不是该别名。历史上的 INTEGER PRIMARY KEY DESC 列声明也有例外，不要机械匹配含 INTEGER 的文本。
- AUTOINCREMENT 仅适用于 INTEGER PRIMARY KEY，防止复用以前已提交的 ROWID，增加维护开销；不保证连续无缺号，也不是普通自增的必要条件。
- 使用全局唯一文本 ID 是合理设计，通常显式写 TEXT PRIMARY KEY NOT NULL。评估文本键对索引宽度的影响，但不要无业务原因更换既有 ID。
- 主键只是选定的候选键；示例订单有整数 order_id，但业务订单号 order_ref 仍需单独 UNIQUE，不能认为有主键就满足全部业务唯一性。其他系统若按租户唯一，则明确相应组合键。先检查既有重复和 NULL 规则。
- 联合主键用于关系记录时，应确认是否存在重试、重修、版本等维度；不能用错误的唯一约束丢弃合法历史。
- WITHOUT ROWID 对某些较短的非整数/复合主键表可能节省空间，但其二级索引携带主键，宽主键可能反而增大成本；它不提供 rowid、AUTOINCREMENT、相同的 last_insert_rowid() 行为，部分 BLOB API 也不适用。结合负载测试后选择。

## 约束表达业务，而不是随意补默认值

- 必填字段 NOT NULL；非空文本另用 CHECK(length(trim(name)) > 0)，因为 NOT NULL 允许空字符串。
- 对取值范围、布尔值和有限状态使用 CHECK。合法状态集合需从业务获取，不要把示例枚举擅自写进真实数据库。
- 单列 CHECK 只能限制合法值，不能代替完整状态转换规则；状态更新可用 WHERE id = ? AND status = ? 检查预期旧状态，并检查实际影响行数。
- 默认值应是真实默认行为，例如 created_at 的统一时间来源；不凭空默认外键、金额或未知状态。
- 外键父键须是可引用的主键/唯一键，组合与排序规则需匹配。子键为 NULL 时通常不要求父记录；必填关系需 NOT NULL。
- SQLite 不自动为子表外键创建索引。是否补索引取决于关联查询、父行更新/删除与子表规模。
- 级联删除只适用于子数据随父记录消亡的业务。审计历史是否必须保留要单独判断，不默认 CASCADE。

## JSON、快照和生成列

- JSON 用于扩展字段、原始报文或不可变快照可以合理；“有 JSON 就违反范式”不是有效评审结论。
- 若 JSON 与独立列重复表达可变状态，确定唯一事实来源、原子更新方式与一致性校验。避免两个来源独立修改。
- 稳定且高频筛选、关联、约束的字段优先使用明确列，必要时从 JSON 提取为生成列或建立表达式索引。
- 文本 JSON 可用 CHECK(json_valid(metadata))；若允许 NULL，明确约束含义。该函数依赖 JSON 能力，目标构建要探测。
- VIRTUAL 生成列在读取时计算，STORED 在写入时保存；都可建立索引。生成表达式须符合确定性等限制，不能含子查询或窗口函数。
- 不能用 ADD COLUMN 随意添加 STORED 生成列；按运行时限制选择重建。生成列不能像普通输入列一样插入值，复制表时使用明确列清单。

## 结构评审应给出的证据

- 重复索引：指出原约束/索引、候选冗余索引及比较依据，保留唯一性和排序规则差异。
- 缺失约束：指出具体业务不变量，以及现有数据是否满足；不能从字段名字推断真实规则。
- JSON 冗余：说明是快照还是重复的可变事实，并指出同步方式，不机械要求拆表。
- 类型不合适：用计算、排序、范围或精度需求证明问题；风格清理与数据错误分开。

## 可运行模板

使用 [order_schema.sql](../assets/order_schema.sql) 查看独立生成的客户、商品、订单、订单明细模型。订单有整数主键和唯一业务订单号；商品当前价格与订单行成交单价有不同业务含义，保留成交单价是历史事实，不是需要消除的重复。

模板假设订单状态为 pending/paid/cancelled，时间为 UTC Unix 秒，金额为整数分，订单行不允许同一商品出现两次。这些均是演示约定，实际使用需检查是否支持拆行、折扣、退款或历史版本。
